## Working Rules

- Do not turn raw sources into requirements, standards, public docs, or tasks without review.
- Keep source/provenance links for every meaningful change.
- If root CORD created a project inbox item with `exact_auto_route` or `high_auto_route`, do not repeat root routing approval. Start planning-first: identify affected artifacts, next backlog/review/Do, blockers, and what still needs approve.
- After every meaningful project change, update `Artifacts/Project_Passport.md` frontmatter: `last_activity_at`, `last_activity_kind`, and `last_activity_ref`.
- After every meaningful change that changes project understanding, update `Artifacts/Project_Dashboard.md`: `last_sync_at`, `last_sync_ref`, and the short sections that changed.
- Do not refresh `Artifacts/Project_Dashboard.md` from route-only reviews or source counts; dashboard changes need approved decision or applied Do that changes project understanding.
- For cross-project handoff, keep `observed_signal` separate from `agent_interpretation`; receiving project chooses diagnosis, R-codes, skill and executor inside its own rail.
- When writing documentation, use Obsidian wikilinks for internal CORD references and do not leave unlinked notes.
- Use the project scaffold folders; do not create loose notes outside the route.
- Before Do, check whether an existing script, skill, MCP, connector, or local tool can execute the action; if not, create a tool gap proposal.
- For local iRidi MCP tools, use the shared gateway after preflight: `http://127.0.0.1:3100/status`, then `http://127.0.0.1:3100/servers/<name>/mcp` for `telegram`, `omnidesk`, `google`, `redmine`, `bus77`, `transcribe`, `tts`, `fathom-archive` и local `bitrix`; do not spawn duplicate stdio MCP from a project agent. Do not confuse local `bitrix` with remote `bitrix24-*`; do not confuse gateway `fathom-archive` with direct remote `fathom` at `https://api.fathom.ai/mcp`.
- Record Do execution trace: tool used, changed artifacts, checks, evidence, and remaining blockers.
- For a new/changed Review or Inbox item, use `cord_inbox_monitor.py --project PROJECT --apply` or `cord_intelligence_policy.py observe --path PATH --apply` before decision; after decision record the exact outcome. Apply only AUTO-1..4 conditions, keep semantic decisions shadow-only, and preserve all human-only gates.
- Use [[03_Resources/Intelligence_Engine/Contracts/Role_Interaction_Contract_v1]] for dialogue: restore the primary goal, choose mode by result lifecycle, lead with the user-visible effect, and never turn raw sessions or routine machine queues into owner work.
- Use learned interaction patterns as dialogue guidance only. Semantic route predictions remain SHADOW-2 until evidence thresholds and explicit promotion approval are satisfied.
- If a missing rule appears 2+ times, update this file or create a CORD_System improvement proposal.
- Run graph/scaffold checks after structural changes.
- Use proposal -> approve -> apply -> archive for standard/canon changes.
- Do not publish internal, personal, draft, or unapproved material to public docs.
- Do not create firmware/code tasks when hardware, protocol, or acceptance facts are missing.
- Do not copy large source-owned dumps into CORD; link source contracts and use approved retrieval routes.
