# Проект 77 Стандарт iRidi — инструкции для агента

## Миссия проекта

Поддерживать **«Стандарт автоматизации iRidi»** как живую энциклопедию технических решений Bus77: принимать новые знания из встреч, экспертных советов, поля и релизов продуктов → класть **обработанную выжимку в `inbox/`** → **предложить правки** в книгу и Wiki → после согласования с Василием перенести папку в `**archive/`**.

Проект **не заменяет** авторов: агент готовит черновики и `proposal.md`; публикация в Google Doc / Wiki — только после вашего решения (`applied` / `rejected` / `partial`).

---

## Цели

1. **Единый канон** для инсталляторов, продаж, пресейла, Project Tool и ИИ.
2. **Скорость** — убрать узкое место «схемы и техрешения» за счёт структуры, шаблонов и автогенерации.
3. **Синхронизация отделов** — сырой поток в коллектор, обработка своим органайзером, общий выход в стандарт/Wiki.
4. **Двусторонняя связь с Wiki** — внутренняя книга полнее; Wiki — проверенное подмножество для внешней аудитории.
5. **Трассируемость** — каждое дополнение ссылается на источник (встреча, тикет, экспертный совет, объект).
6. **Очередь inbox → archive** — ни одна правка в канон без прохождения согласования и архивации решения.

## Inbox и archive — workflow агента

### Назначение


| Папка          | Роль                                                                                                 |
| -------------- | ---------------------------------------------------------------------------------------------------- |
| `**inbox/**`   | Обработанная информация, которую агент **берёт в работу** и по которой готовит предложения изменений |
| `**archive/`** | Материалы, по которым **согласование завершено** (изменения применены **или** отклонены вами)        |


Сырьё (полный транскрипт, сырой лог) **не кладётся** в inbox — только структурированная выжимка + ссылка на источник в `meta.yaml`.

### Жизненный цикл

```
Источник (встреча / поле / релиз / …)
    → обработка (человек или агент)
    → inbox/YYYY-MM-DD_slug/   [status: pending]
    → агент: proposal.md       [status: in_progress → review]
    → согласование с Василием
         ├─ applied   → правки в книгу/Wiki → archive/
         ├─ rejected  → archive/ (без правок в канон)
         └─ partial   → часть в канон → archive/ + при необходимости новый slug в inbox
```

### Статусы (`meta.yaml`)


| status                             | Где     | Кто меняет                        |
| ---------------------------------- | ------- | --------------------------------- |
| `pending`                          | inbox   | тот, кто положил материал         |
| `in_progress`                      | inbox   | агент                             |
| `review`                           | inbox   | агент (proposal готов)            |
| `applied` / `rejected` / `partial` | archive | агент после вашего явного решения |


### Обязанности агента

1. **При старте сессии по стандарту** — просмотреть `inbox/` на `pending` и `review`.
2. **Взять в работу** — обновить `status: in_progress`, заполнить `proposal.md` (целевые разделы, черновик текста, Wiki, риски).
3. **Отдать на review** — `status: review`, кратко сообщить вам список папок.
4. **До согласования** — не менять Google Doc, Wiki, `remarks`.
5. **После вашего «применить» / «отклонить»**:
  - дописать `resolution.md` и финальный `meta.yaml` (`resolution`, `resolved_at`, ссылки на правки);
  - **переместить** всю папку `inbox/…` → `archive/…` (имя slug сохранить);
  - убедиться, что в inbox папки не осталось.

### Команды-триггеры (от вас)


| Фраза                                       | Действие агента                                 |
| ------------------------------------------- | ----------------------------------------------- |
| «разбери inbox» / «что в очереди стандарта» | список `pending` + `review`, приоритеты         |
| «предложи правки по …»                      | взять указанный slug, сделать `proposal.md`     |
| «применяем» / «ок, в книгу»                 | внести правки, `resolution: applied`, → archive |
| «отклонить» + причина                       | `resolution: rejected`, → archive               |
| «частично»                                  | зафиксировать что вошло, `partial`, → archive   |

## Структура технической книги (шаблон подсистемы)

По спецификации в `remarks` / реестре книг каждая ТК содержит:

1. Общее представление о системе и возможностях
2. Основные управляющие элементы (модули, датчики, выключатели)
3. Источники / исполнительные устройства и особенности
4. Порядок и особенности монтажа
5. **Рабочие схемы** (узкое место — приоритет для агента-оформителя)

Пример оглавления книги «Освещение» (Drive): гл. 1 кейсы → гл. 2 описание системы → гл. 3 управляющие элементы → гл. 4 источники света → гл. 5+ схемы.

## Процесс обновления (с встречи 30.06.2026)

```
Событие (экспертный совет / поле / релиз / встреча)
    → коллектор (сырые данные)
    → органайз отдела
    → обработанная выжимка → inbox/ (локальная очередь проекта)
    → агент: proposal.md → согласование с Василием
    → applied: Google Doc + Wiki (+ remarks при необходимости)
    → папка → archive/
    → QA автора раздела / редактор (Маша) — по критичности раздела
```

**Ритм:** еженедельный слот автора на approve предложений ИИ (обсуждалось: «понедельник 11:00–12:00»). Локальный inbox можно разбирать чаще — по команде «разбери inbox».

## Антипаттерны

- Не путать **стандарт** с **Miro/чертежами** или произвольными Google Doc (см. `snippets.yaml`).
- **Не править книгу/Wiki в обход inbox** — сначала `proposal.md`, потом согласование, потом archive.
- **Не оставлять решённые папки в inbox** — только в `archive/`.
- Не публиковать в Wiki без пометки источника и approve.
- Не дублировать между главной книгой и Drive-книгой без явной «короткой/полной» версии.
- Не «кормить» коллектор только обработанным текстом — сохранять сырьё (коллектор) отдельно от inbox (выжимка).
- Не искать ответы чтением всего `knowledge.yaml` — `memories/scripts/query_index.py`.
