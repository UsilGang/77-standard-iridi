# Версионность «Стандарта автоматизации iRidi»

Черновик для выбора схемы. Текущая отметка в реестре замечаний: **1.2** (лист «ТК SH Архитектура»).

## Актуальная рекомендуемая модель для architecture review 2026-08-05

Подробное обоснование: [[01_Projects/001_77_Standard_iRidi/Artifacts/Documentation/Editorial_Assignment_And_Versioning_Model_v1]].

- книга: одна release SemVer `MAJOR.MINOR.PATCH`;
- любое опубликованное изменение повышает минимум PATCH;
- до публикации используется `draft build ID`, release version не меняется;
- chapter/section/topic/rule/asset: монотонная `revision` + digest + `introduced_in/last_changed_in`, без собственного SemVer;
- самостоятельный module SemVer — только для отдельно публикуемой и поддерживаемой книги;
- каждое изменение связано цепочкой `source -> EDT -> changed UID revisions -> changeset -> release`;
- changelog генерируется из editorial assignments и release manifest.

Варианты ниже сохранены как история анализа. Вариант B с четырьмя октетами и SemVer каждой обычной главы не рекомендуется: он смешивает identity, location и release state.

---

## Зачем версия

- Продажи и инсталляторы понимают, **на каком каноне** их обучали.
- ИИ и inbox/archive ссылаются на **конкретное состояние** книги (`applied` при версии `2.3.1`).
- Wiki публикует **подмножество** с пометкой «актуально для стандарта ≥ X.Y».
- Drive-книги по подсистемам могут жить **своим циклом**, но входят в составное имя главной книги.

## Классы изменений (общая шкала сложности)

Используется во всех вариантах ниже.

| Класс | Код | Примеры | Риск для проектов |
|-------|-----|---------|-------------------|
| **E0 Редактура** | `edit` | орфография, пунктуация, переносы, ссылки без смены смысла | нет |
| **E1 Уточнение** | `clarify` | переформулировка без смены рекомендации; «что имелось в виду» | низкий |
| **E2 Дополнение** | `add` | новое техрешение в существующем подразделе; новая схема; новый артикул | низкий |
| **E3 Пересмотр раздела** | `revise` | существенная переписка раздела/подраздела; смена рекомендуемой топологии | средний |
| **E4 Новый блок** | `new-block` | новый подраздел 4.11; новая глава в Drive-книге; пустой разд. 7 впервые наполнен | средний |
| **E5 Новый домен** | `new-domain` | новый раздел верхнего уровня (напр. «18. Безопасность»); новая подсистема в оглавлении | высокий |
| **E6 Структура / политика** | `breaking` | перенумерация, слияние разделов, смена обязательных правил («раньше можно, теперь нельзя») | **ломающий** |
| **E7 Отмена** | `deprecate` | явный запрет устаревшего решения; «не применять на новых объектах» | **ломающий** |

**Правило:** один релиз книги = **максимальный** класс среди всех правок в пакете (inbox → archive batch).

## Вариант A — SemVer 3 октета (простой, рекомендуемый старт)

Формат: **`MAJOR.MINOR.PATCH`**

| Октет | Когда увеличивать | Классы изменений |
|-------|-------------------|------------------|
| **MAJOR** | Ломающие изменения для новых проектов | E6, E7 |
| **MINOR** | Новая существенная функциональность канона | E4, E5, E3 (если меняется рекомендация «как делать») |
| **PATCH** | Без смены рекомендаций | E0, E1, E2 |

Примеры:
- `1.2` → `1.2.1` — исправили термины в 4.1 (E1).
- `1.2` → `1.3.0` — добавили раздел 5.4 с новым кейсом диммирования (E4).
- `1.3` → `2.0.0` — раздел 4.6: сценарии на шине объявлены обязательными иначе, чем раньше (E6).

**Плюсы:** все уже знают SemVer; совпадает с «1.2» в таблице замечаний.  
**Минусы:** не видно, *какой* раздел менялся; несколько MINOR подряд без MAJOR не отражают «зрелость» раздела.

**Где хранить:** титул Google Doc + строка в `remarks` + `version.yaml` в проекте + поле в `archive/.../meta.yaml`.

## Вариант B — SemVer 4 октета «книга → раздел → подраздел → правка»

Формат: **`EDITION.CHAPTER.SECTION.PATCH`**

| Октет | Смысл | Инкремент |
|-------|--------|-----------|
| **EDITION** | Поколение всей книги | E6, E7; полная реструктуризация оглавления |
| **CHAPTER** | Верхний раздел 1–17 | E5; первое «официальное» наполнение пустого раздела; E3 по всему разделу |
| **SECTION** | Подраздел (4.1, 5.2…) | E4; E3 в пределах одного подраздела |
| **PATCH** | Точечные правки | E0, E1, E2 в пределах того же подраздела |

Примеры:
- `1.4.0.0` — стабильная «четвёртая глава» (архитектура), подразделы ещё 0.
- `1.4.2.0` — дописали 4.2 «Архитектура системы» (E4).
- `1.4.2.3` — три пакета уточнений в 4.2 без смены рекомендаций.
- `2.0.0.0` — перенесли Bus77 из разд. 4 в отдельную книгу, сменили оглавление (E6).

**Плюсы:** по номеру видно, **где** жила последняя смысловая правка; удобно для ИИ-маршрутизации.  
**Минусы:** сложнее объяснять продажам; при правках в двух разделах за один релиз — неоднозначность (см. правило ниже).

**Правило пакета:** при нескольких разделах в одном релизе — поднимать **старший** затронутый октет; младшие обнулять справа.  
Пример: правки 4.2 (E4) + 5.1 (E2) → `1.4.3.0` (главный драйвер — SECTION для 4.2), в changelog перечислить оба.

## Вариант C — Двойная версия: Edition + SemVer

Формат: **`2026.2` + `2.5.3`** (две независимые метки)

| Метка | Назначение |
|-------|------------|
| **Edition `YYYY.N`** | «Выпуск года» для печати/PDF, обучения, договоров; N = порядковый выпуск в году |
| **SemVer `X.Y.Z`** | Техническая версия канона (как вариант A) |

Примеры:
- Обучение продаж Q3: «работаем по edition **2026.2** (semver ≥ 2.4.0)».
- Мелкие правки в течение квартала: `2.4.1`, `2.4.2`, edition не меняется.
- К концу года сборка PDF: edition `2026.3` = снимок semver `2.7.0`.

**Плюсы:** разделяет «маркетинговый выпуск» и «живые правки».  
**Минусы:** две цифры путать легче; нужна таблица соответствия.

## Вариант D — Составная: главная книга + модули Drive

Формат главной: **`MAJOR.MINOR.PATCH`**

Каждая Drive-книга: свой **`MAJOR.MINOR.PATCH`**

Составное имя в шапке главной книги:

```text
Стандарт iRidi 2.3.0
  ├─ architecture 1.4.0  (Drive: Архитектура Bus77)
  ├─ lighting     1.2.1  (Drive: Освещение)
  ├─ climate-hvac 0.9.0  (черновик)
  └─ …
```

| Событие | Что растёт |
|---------|------------|
| Правка только в Drive «Освещение» E2 | `lighting` PATCH; главная MINOR только если выжимка в разд. 5 обновлена |
| Синхронизация разд. 5 главной с Drive | главная MINOR + фиксация `lighting@x.y.z` в changelog |
| E6 в одной Drive-книге | её MAJOR; главная MAJOR если меняется обязательная политика для всего стандарта |

**Плюсы:** отражает реальную структуру (17 разделов + отдельные ТК).  
**Минусы:** больше учёта; агенту нужен `version.yaml` с матрицей модулей.

## Вариант E — Версия + класс изменения (тег)

Формат: **`2.3.1+clarify`** или **`2.4.0+new-block`**

SemVer (вариант A) + **обязательный тег класса** последнего релиза.

**Плюсы:** одна цифра для людей, класс — для агента и аудита.  
**Минусы:** нестандартный синтаксис для внешних.

## Рекомендация (гибрид A + D + элемент C)

**На старте:**

1. **Главная книга** — `MAJOR.MINOR.PATCH` (вариант A), продолжить с **1.2.0** или **2.0.0** (если объявить «второе поколение» после inbox-процесса).
2. **Drive-книги** — отдельный semver; в `version.yaml` проекта матрица модулей.
3. **Раз в квартал** (или перед обучением) — необязательный **Edition** `2026.Q2` = снимок PDF + зафиксированный semver.

**Кто поднимает версию:** вы при `applied` в archive; агент **предлагает** октет и класс E0–E7 в `proposal.md`.

**Changelog:** один файл `CHANGELOG.md` в корне проекта + краткая строка в Google Doc (раздел 1 или титул).

## Связь с inbox / archive

В `meta.yaml` архива после согласования:

```yaml
version_bump:
  proposed: "1.3.0"           # агент в proposal
  approved: "1.3.0"           # вы подтвердили
  change_class: new-block     # max E4
  sections: ["5.4", "5.4.2"]
  modules:
    book-main: "1.3.0"
    lighting: "1.2.0"
  wiki_min_version: "1.3.0"   # если Wiki обновлялась
```
